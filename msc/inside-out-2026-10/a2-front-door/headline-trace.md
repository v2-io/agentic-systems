## 3. What D.3 would build

D.3: "every front-matter sentence that restates a result carries that result's slug, so a diff can check it." I.7: "a diff fails when the cited body has changed." Half of this landed; half is a tool question; the gap between them has evidence.

**Landed.** Every headline sentence carries the slug(s) it restates, inline and visible, in the house style ( #slug ). INTRODUCTION is the register: the end-of-line comment `<!-- headline:Hn · Part · restates: … -->` on each item names the headline id, its Part and its restated slugs. `resolve_preface_transclusion` (`bin/lib/ingest.rb` :632) strips `<!--.*?-->` before the monograph build, and md-press leaves HTML alone, so the comments cost the reader nothing. The Part I front and the README partial carry one comment each naming which headlines they restate. No new register file: a `HEADLINES.md` would be a fifth front surface that itself has to agree.

**The evidence that this is not yet a check.** Two rows, both from vsect's own output. (i) Before this round, the Part I round-4 checker recorded a `✓~ read-check` whose criterion is *about* INTRODUCTION headline 1 but which is *bound to* `segment:result-persistence-condition`: an edit to INTRODUCTION lapses nothing, because INTRODUCTION is not a record. My nine checks (`reviews/a2-front-door-trace-1.md`) have the same shape by necessity. (ii) When `vsect take` read them, it ignored five of my `read:` entries: `deriv-persistence-cost` is not in `result-persistence-condition`'s basis, `deriv-stochastic-non-exit` and the sketch are not in `deriv-sector-condition`'s, the wrapping segment is not in `der-directed-separation`'s, and `deriv-observation-noise-placement` is not in the tempo-advantage segment's. A headline restates a *set* of segments that need not be each other's dependencies, so a check bound to one of them lapses only when that one changes. An edit to `#deriv-persistence-cost` would leave H1's price clause unguarded.

**The design, for I.4/I.7 and the vsect builder** (the store migration is in flight; this is a kind, not a normalizer change). Declare a record kind `front` in `.vsect/kinds.yaml`, grain record, `find:` the front-surface files (`01-aat-core/INTRODUCTION.md`, `doc/readme/src/_position-and-lineage.md`, and the Part fronts once each is its own file, below), with one edge field `restates`, in the basis and bearing meaning (an edit upstream lapses the front's checks, with the cause named), *not* `broken` on refute (a refuted result makes the headline *wrong*, which is a finding to open, not a cascade to run; this differs from `depends:` and is worth the builder's judgment). The `restates:` list is read from the headline comments, or from frontmatter once `resolve_preface_transclusion` strips frontmatter too (today it strips comments and the leading heading, so frontmatter would render into the monograph; a small build change). Then: a check on `front:introduction` with `--read` naming the restated segments lapses when any of them changes, `vsect open` shows `front:introduction ↻ stale: upstream changed (segment:deriv-persistence-cost)`, and the second mind's `vsect confirm` is the step that re-reads the sentence. That is I.7's "diff fails" in the form the record already has for segments, with no new tool. The surfaces that are inside `OUTLINE.md` (the Part fronts) are too coarse a grain inside that file; the transclusion mechanism INTRODUCTION already uses (`![[NAME]]`, any lone-embed prose chunk, `ingest.rb` :548) would let each Part front live in its own file and be its own record. H.1 owns the Part fronts' content; the move is mechanical and I did not make it in this round.

**A small deterministic check beside it** (`bin/check-headlines`, not built): read INTRODUCTION's headline comments as the register; for each surface in a hardcoded table (the way `build-readme` hardcodes TARGETS) with its Part filter, confirm that every headline assigned to it is cited there by at least one restated slug, that every restated slug names a file, and that no surface cites a headline the register does not have. That is the "agree on one list" half, mechanical, suitable for `bin/check-commit`'s table. The "same register" half is a mind's, and vsect is where it is recorded.
