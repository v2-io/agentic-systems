**The scaffold homonym (the point I would put first for the integrator).** Canon's "scaffolding" (`#scope-scaffolded-logogenic`; 49 files hit) is *architecture*: a multi-step loop around the model, external state $M^{\text{ext}}_t$, tool use as a Pearl Level-2 channel, structured context assembly. The census's "scaffold" is a *product feature that compensates for what the model cannot yet do* ("scaffolds compensate until models absorb them", Joseph's D25 framing; examples: todo tools, the Think tool, edit-repair and fuzzy-match layers, LLM-judged loop detection, prompted XML tool calling, memory-tool coaching, file rollback, Handoff). The two senses overlap but do not coincide, so the census's central finding (twelve withdrawals from 2026-01 at six vendor groups state the model as the reason; Claude Code gates its todo tools by model and keeps them for older ones) is **not evidence against** canon's "scaffolded loops are not engineering convenience but a load-bearing requirement for recovering Part II's persistence guarantees" (`#impl-scaffolded-logogenic`, **[verified]** quoted text). Read honestly, it *stratifies* the scaffold set, and canon has no such stratification:

- **What retires per model generation**, per the records: crutches for step-level deliberation and tool use (todo lists; the Think tool; edit repair; LLM loop-judging; XML tool calls; memory-tool coaching). Several of these sit where canon says a *chain-of-thought approximates the cascade* inside the forward pass (`#def-coupled-update-dynamics`, "Chain-of-thought as approximate cascade", **[verified]**). The records give the model-side reason: zed's "models now have their own first-class thinking APIs" (2026-02), Claude Code's Think tool leaving its build beside native thinking (2025-03), kimi-cli's six days after supporting K2's thinking mode.
- **What stays or spreads**, per the records: compaction (amp removed it for Handoff in 2025-10, reversed 2026-05: "Today's leading frontier models are great at handling compaction … we had to shut it off for a day and everyone complained"; 16 of 21 long-present vendor groups mention it by 2026Q3); background consolidation ("dream" at seven or more vendor groups between 2026-04 and 10; the census itself says copying is not ruled out); deterministic loop guards (13 harnesses, after an LLM-judged variant was withdrawn); guards against stopping early (arriving, model-failure-keyed); Claude Code's instruction never to "fabricate or predict" a pending subagent result, kept through five Opus releases.
- *My reading, from the shape and not tested:* what retires resembles canon's loop-level cascade recovery where the forward pass has taken the job over; what stays resembles canon's $M^{\text{ext}}_t$ persistence and event-ordering machinery (state across boundaries; correct handling of not-yet-arrived observations). Exceptions in the same records weaken any clean split: amp *retired Handoff and file rollback* "as models advanced", and the compaction thread itself is mixed (`wh.compaction-spread-and-stayed` lists a withdrawn micro-compaction variant at kimi-code; `kano.compaction.must-be-from-2026` exists by slug, which I did not read). So this is a hypothesis for a strengthening attempt, in the project's own register, not a result: for each retired scaffold, which canon function did it serve, and does that function survive at the forward-pass level or elsewhere?
